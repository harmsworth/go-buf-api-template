> 约束：**不引入 ent**、**不引入 DDD 三层目录**（保持 package-by-feature）、继续 wire、继续 Gin+gRPC+gateway 三入口。
> 目标：**每个业务包减文件、减行数**，同时提升可测试性与接线清晰度。

> **状态（2026-09-23）**：S0–S6 已全部落地，详见 [进度看板](./README.md)。

## 〇、一句话结论

kratos 那套"特别"的 wire 加载，**70% 的价值来自"接口倒置 + 装配集中 + 测试双打法"，只有 30% 来自 wire 机制本身**——在 7 个 provider 的规模下，手写一个 7 行的装配函数和 wire 生成的等价。
所以要抄的是它的**边界设计**，不是它的**目录形态**：把 `Repository` 接口做成真正的替换点、把装配收敛到 `cmd/server/providers.go` 一处、用 `errorsx`/`httpx`/`grpcx`/`aipgorm` 四个 platform 包抽走重复代码。
最终每个业务包从 **6 文件 → 5 文件**（todo 699→~587 行，user 1096→~931 行），`main.go` 271→~55 行，`NewApp` 签名被永久冻结。

## 一、kratos-layout 的 wire 加载方式：机制拆解

### 1.1 它实际上做了三件事

**(1) `wireinject` 双文件共存** —— 声明与实现同包同名，靠构建标签互斥

- `cmd/server/wire.go:1-4`：`//go:build wireinject`，函数体只有 `panic(wire.Build(...))`，**不参与 `go build`**，只给 wire 工具用 AST 读依赖图。
- `cmd/server/wire_gen.go:1-5`：`// Code generated by Wire. DO NOT EDIT.` + `//go:build !wireinject`，是真实实现，**且入库**（`.gitignore` 无 `*_gen.go` 条目，`.gitattributes:15` 只把 `wire_gen.go` 标记为 `linguist-generated=true` 以折叠 PR diff）。
- `wire_gen.go:3` 的 `//go:generate go run -mod=mod github.com/google/wire/cmd/wire` 写在**生成文件自己体内**，所以 `Makefile:29` 的 `go generate ./...` 会递归触发它（同一命令也触发 ent 生成，两者无法单独跑）。

**(2) ProviderSet 按层分组** —— `wire.Build` 一行写死，加资源不动 cmd

| ProviderSet | 位置 | 成员 |
| --- | --- | --- |
| `server.ProviderSet` | `internal/server/server.go:8` | `NewGRPCServer, NewHTTPServer` |
| `service.ProviderSet` | `internal/service/service.go:6` | `NewTodoService` |
| `biz.ProviderSet` | `internal/biz/biz.go:6` | `NewTodoUsecase` |
| `data.ProviderSet` | `internal/data/data.go:15` | `NewData, NewTodoRepo` |


`wire.go:23` 一行：`panic(wire.Build(server.ProviderSet, data.ProviderSet, biz.ProviderSet, service.ProviderSet, newApp))`。
**这正是你觉得"特别"的点**：业务代码里看不到任何注册语句，也没有 Service Locator、没有 `init()` 自注册——装配规则集中在一个 24 行文件里，且加资源时**这个文件不动**。

**(3) 构造函数返回接口 + 接口放在 biz** —— 依赖倒置的可执行形式

```go
// internal/data/todo.go:36 —— 全仓唯一返回接口的构造函数
func NewTodoRepo(data *Data) biz.TodoRepo { return &todoRepo{data: data} }   // todoRepo 未导出
// internal/biz/todo.go:49 —— 接口由消费方（领域层）声明
type TodoRepo interface { FindByID(...); ListTodos(...); CreateTodo(...); UpdateTodo(...); DeleteTodo(...) }
// internal/biz/todo.go:102
func NewTodoUsecase(repo TodoRepo) *TodoUsecase
```

返回接口带来两个连锁效应：① wire 图中不需要任何 `wire.Bind`（**全仓 0 处 `wire.Bind`/`wire.Value`/`wire.Struct`**）；② `*todoRepo` 从未出现在 `wire_gen.go` 里，实现类型彻底封死在 data 包内。

### 1.2 完整加载链（`wire_gen.go:26-40`，拓扑排序后）

```
main(): flag -conf → configs/config.yaml + env KRATOS_* → Scan → conf.Bootstrap
        → 手工构造 logger、然后是三个"根对象"喂给 wire: (*conf.Server, *conf.Data, *slog.Logger)
wireApp(*conf.Server, *conf.Data, *slog.Logger):
  ① data.NewData(confData)                  (*Data, func(), error)  ← 唯一带 cleanup 的 provider
  ② data.NewTodoRepo(dataData)    → biz.TodoRepo   ★ 返回接口
  ③ biz.NewTodoUsecase(todoRepo)  → *biz.TodoUsecase
  ④ service.NewTodoService(uc)    → *service.TodoService
  ⑤ server.NewGRPCServer(confServer, todoService)  → v1.RegisterTodoServiceServer(srv, todo)
  ⑥ server.NewHTTPServer(confServer, todoService)  → v1.RegisterTodoServiceHTTPServer(srv, todo)
  ⑦ newApp(logger, gs, hs)        → kratos.New(... kratos.Server(gs, hs))
main(): defer cleanup() → app.Run()
```

**同一个 `*TodoService` 实例同时被 ⑤⑥ 挂载**（wire 单例语义），因为它的方法签名对 gRPC 的 `TodoServiceServer` 和 HTTP 的 `TodoServiceHTTPServer` 是结构化兼容的——编译期校验发生在两个 `Register*` 调用的形参上。

### 1.3 好在哪里（有据可查）

1. **零运行时开销、零反射**：生成物就是 15 行纯顺序 Go 代码，与手写 DI 完全等价。
2. **`wire.go` 写一次永不再改**：新增资源只动各层 ProviderSet，**`cmd/` 零改动**（这是 ProviderSet 唯一的实质收益）。
3. **cleanup 自动逆序聚合**：`NewData` 返回 `(*Data, func(), error)`，wire 按构造逆序调用（当前只有 1 个，但机制在多资源时省人脑）。
4. **接口即替换点**：`data.NewTodoRepo → biz.TodoRepo`，所以 `service/todo_test.go:31` 的 `newFakeTodoRepo() biz.TodoRepo` 能无缝顶替。
5. **测试双打法分工清晰**：service 层用 fake repo（`todo_test.go:23-33`）+ 手写 gRPC stream fake；data 层用**内存 SQLite 跑真实 ent**（`data/todo_test.go:22-36`，`modernc.org/sqlite`，`NewTodoRepo(&Data{db: client})` 直接字面量构造 Data）。
6. **依赖方向由 go mod + 约定锁死**：service/biz 对 `internal/data` 的 import 数为 **0**（`AGENTS.md:41-46` 写成硬规则）。

### 1.4 代价与"不好"的地方（这是你直觉里那点不对劲）

| # | 问题 | 证据 |
| --- | --- | --- |
| 1 | **4 个纯业务包被 DI 框架污染** | `biz.go:3`、`service.go:3`、`data.go:11`、`server.go:4` 都 `import "github.com/google/wire"`；`biz` 本该是零第三方依赖的领域层 |
| 2 | **服务注册仍是手工的，且要改函数签名** | 加资源要改 `NewHTTPServer(c *conf.Server, todo *service.TodoService)` 的**形参列表**（`http.go:16` / `grpc.go:13`）——ProviderSet 完全没吸收这块 |
| 3 | **返回接口封死了同类型多实现** | 再加一个 `biz.TodoRepo` 实现会触发 wire multiple bindings；而"返回接口"这条硬规则恰恰是让多实现变难的那条（可用 `wire.Bind` 解，但全仓没用） |
| 4 | **CI 不校验生成物新鲜度** | `.github/workflows/go.yml:45-49` 只有 build + test。忘跑 `make generate` 时，报错出现在 `wire_gen.go` 编译失败，而若恰好能编译则**绿灯上线、服务没注册** |
| 5 | **wire 报错定位差** | 缺 provider 时报 `wire.go:23:2: no provider found for biz.OrderRepo`，指向 Build 那一行而非真实缺失点 |
| 6 | **中间件不对称，wire 发现不了** | `http.go:18-28` 有 `recovery` + `validate.Validator`（field_behavior 校验），`grpc.go:14-18` **只有 recovery**——gRPC 通路上的 REQUIRED 校验是缺的 |
| 7 | **gRPC 侧有编译期盲区** | `TodoServiceServer` 含 `mustEmbedUnimplemented...`，导入 credentials: 只重新生成 proto 而忘记实现新方法时，gRPC 侧**编译通过**（Unimplemented 兜底）、运行时才报错；只有 HTTP 的结构化接口会编译失败 |
| 8 | **`wire.go` 与 `wire_gen.go` 双份维护** | 改 provider 签名必须记得重生成；`automaxprocs` 的 blank import 被 wire 复制进生成文件（`wire_gen.go:20`） |


### 1.5 关键技术判断：**可测试性不是 wire 给的**

`internal/service/todo_test.go` 与 `internal/data/todo_test.go` **一行 wire 都没用**（全仓 `wire.` 的 6 处命中，0 处在 `*_test.go`）。
它们干净是因为三个前提：① `NewTodoRepo` 返回接口；② `NewTodoUsecase` 形参是接口；③ 构造函数全是普通函数（无 `init()`、无包级单例、无 Service Locator）。
**把 wire 摘掉改成手写 `main()`，这两个测试一行都不用改。**
→ 所以：**抄这套方案的收益主要在"接口边界 + 装配集中"，不在 wire 本身。**

### 1.6 对 go-buf-api-template 的取舍：**抄什么 / 不抄什么**

| kratos 做法 | 是否抄 | 理由 |
| --- | --- | --- |
| 接口放在领域层作为替换点 | ✅ 抄（你现在已在 service.go 声明 `Repository`，方向对了） | 但要把它变成**真正的**替换点（见 S1） |
| 装配集中、加域只改一处 | ✅ 抄，但**做得更干净** | 不往业务包里塞 `wire.NewSet`，改在 `cmd/server/providers.go` 集中，业务包零 wire 依赖 |
| cleanup 三元组聚合 | ✅ 抄 | logger 文件句柄、DB 都由 wire 聚合逆序关闭 |
| 测试双打法（fake + 真存储） | ✅ 抄 | 你现在已有 model/service 测试；补持久层即可 |
| CI 校验生成物新鲜度 | ✅ 抄（kratos 没有，我们补） | wire drift 检查 |
| **每个业务包 `import wire`** | ❌ 不抄 | 你的业务包是完整纵向切片，`model.go` 里躺着 GORM PO 与 `ToProto()`，不该和 DI 容器共享编译单元 |
| **加资源要改 `NewHTTPServer` 签名** | ❌ 不抄，**用切片 provider 冻结 `NewApp` 签名** | 这是能做得比 kratos 更好的地方（见 S4） |
| **DTO/DO/PO 三层 + biz/data/service 目录** | ❌ 不抄 | 你已明确不要 DDD 三层；保持 PO↔Proto 直转 + `Repository` 接口，够用且不膨胀 |
| ent + AutoMigrate | ❌ 不抄 | 保持 GORM + golang-migrate |

## 二、go-buf-api-template 现状痛点（已核实）

| # | 痛点 | 证据 |
| --- | --- | --- |
| 1 | **替换点被封死在构造函数内部** | `todo/service.go:46` `NewService(db *gorm.DB, log)` 内部写死 `newRepository(db)` → 测试只能绕过构造函数写 `&Service{repo: ...}`（`service_test.go:79`、`user/service_test.go:96` 两个逐字重复的 `testService` 跳板） |
| 2 | `newRepository` 私有 + 返回具体类型 | `todo/repository.go:68-71`：`func newRepository(db *gorm.DB) *repository`。注意：若改为"返回具体类型 + `wire.Bind`"，`*repository` 未导出导致 cmd 侧**物理上无法引用**，所以只能返回接口 |
| 3 | 0 处编译期断言 | 全仓无 `var _ Repository = (*repository)(nil)`，接口与实现漂移只能靠那一行赋值隐式报错 |
| 4 | 0 处 ProviderSet | `cmd/server/wire.go` 是 12 项扁平列表；provider 散落在 `main.go:154/225/228/232/248`，main.go 共 271 行 |
| 5 | **双 logger 实例** | `main.go:74` 手工建一个、`wire_gen.go:21` 又注入一个 |
| 6 | `App` 不持有生命周期 | `App` 只有 `Engine`/`GRPC`；cleanup 只有 DB 一个；logger 文件句柄从不关闭 |
| 7 | **4 处平行错误映射且语义分叉** | todo handler `writeStatusError`、user handler `writeDomainError`、todo server `gRPCError(err,msg)`、user server `gRPCError(err)`（签名都不统一）。同一 `ErrInvalidCredentials` HTTP 401 / gRPC Unauthenticated / ChangePassword 又 FailedPrecondition |
| 8 | **handler 层约 125 行逐行重复** | 两个 handler 各自实现 `readProto`/`validateReq`/`writeProto`/`writeError`/`writeStatusError` |
| 9 | **3 个等价的 protovalidate 实例** | todo.NewHandler、user.NewHandler、provideGRPCServer 各 `protovalidate.New()` 一次 |
| 10 | `router.go` 只有 15/28 行 | 与 handler 严格一对一，单独成文件只有成本没有收益 |
| 11 | `NewApp` 随域增长 | 每加一个域加两个形参 + 两处注册 + gateway 一处注册 |
| 12 | **持久层 280 行零覆盖** | `todo/repository.go`(125) + `user/repository.go`(155)，无 `repository_test.go` |
| 13 | AI 规则写死了旧形态 | `.codebuddy/rules/go-service-integrator/RULE.mdc:43-45` 把 `NewService(db *gorm.DB, ...)` 写进规则、`:21-26` 是六文件职责表——**不同步改，下次 AI 生成会把旧形态写回来** |

## 四、分阶段方案

> 依赖顺序：S0 → S1 → S2 → {S3a, S3b, S3c 可并行} → S4 → S5。
> **S1/S2/S3b/S3c/S5 各自合并后系统仍可正常编译运行**，可分批 PR。

### S0：工具链与 CI 地基（0.3 人天）

**改**：`Makefile`、`.github/workflows/quality-gate.yml`、`go.mod`

- `Makefile:4` 的 `WIRE ?= $(GO) run ...wire@latest` → 版本钉死：`go get -tool github.com/google/wire/cmd/wire` 后改为 `$(GO) tool wire ./cmd/server`（若 `-tool` 失败则退为 `@v0.7.0`，与 `go.mod:12` 对齐）。`@latest` 是生成物漂移的直接来源。
- 新增两个 target 并纳入 `check`：

```
test: ## 运行单元测试
	$(GO) test ./... -count=1
wire-drift: ## 检查 wire 生成物是否与 wire.go 同步
	$(WIRE)
	git diff --exit-code -- cmd/server/wire_gen.go \
	  || (echo "wire_gen.go 与 wire.go 不同步，请执行 make wire 并提交" && exit 1)
check: proto-lint proto-breaking proto-generate vet build test wire-drift
```

- CI 的 `go` job 末尾追加两步：`Wire drift check`（`make wire` + `git diff --exit-code`）与 `Unit test`（`go test ./... -count=1`）。

**验收**：本阶段不碰任何 Go 业务代码；手工改 `wire_gen.go` 一个字 → `wire-drift` 必须失败。

### S1：接口边界改造（0.5 人天）

**改**：`internal/todo/repository.go`、`internal/todo/service.go`、`internal/user/repository.go`、`internal/user/service.go`、`cmd/server/wire.go(+wire_gen 重生成)`、两个 `service_test.go`、**`.codebuddy/rules/go-service-integrator/RULE.mdc`**、`internal/platform/logger/logger.go`

```go
// internal/todo/repository.go
var _ Repository = (*repository)(nil)     // ← 编译期断言：接口漂移不再等到运行时

// NewRepository 构造 GORM 仓储实现，供 wire 注入。
// 返回接口而非具体类型是有意权衡：
//  1. wire.Bind 写在 cmd 里时无法引用未导出的 *todo.repository，物理上做不到；直接返回接口可省 Bind；
//  2. 把替换点从 NewService 内部（硬编码 newRepository(db)）上移到 NewService 的形参，
//     单测因此能直接 NewService(fake, log)，不必再绕过构造函数写未导出字段。
func NewRepository(db *gorm.DB) Repository { return &repository{db: db} }
```

```go
// internal/todo/service.go —— 只改构造函数，业务方法零改动
func NewService(repo Repository, log *slog.Logger) *Service { return &Service{repo: repo, log: log} }
```

```go
// internal/platform/logger/logger.go 新增
// Nop 返回丢弃所有输出的 logger，供单测构造依赖使用。
func Nop() *slog.Logger { return slog.New(slog.NewTextHandler(io.Discard, nil)) }
```

- 删除两个 `service_test.go` 里的 `testService` 跳板，调用点改为 `NewService(repo, logger.Nop())`。
- **`RULE.mdc:43-45` 的代码块必须同步更新**（否则 AI 下次会写回 `NewService(db *gorm.DB, ...)`）。

**预期 `wire_gen.go`**：`todoRepository := todo.NewRepository(db)` → `todoService := todo.NewService(todoRepository, slogLogger)`。
注意 `todo.Repository` 与 `user.Repository` 是**不同类型身份**（包名前缀不同），wire 图不会冲突——package-by-feature 的天然红利。

**验收**：

- `grep -rn "\*gorm.DB" internal/todo/service.go internal/user/service.go` → 无结果
- `grep -rn "testService" internal/` → 无结果
- `go build ./...` + `go test ./internal/...` 全绿（测试内容一行没改）

### S2：装配收敛 —— `cmd/server/providers.go`（0.8 人天）

**新增**：`cmd/server/providers.go`；**改**：`cmd/server/wire.go`、`main.go`、`internal/platform/logger/logger.go`

```go
// cmd/server/providers.go —— 新增/删除业务域时的**唯一改动点**
// PlatformSet 汇聚基础设施 provider：配置切片 → 日志 → 数据库 → gRPC Server。
var PlatformSet = wire.NewSet(
	provideLogConfig, provideDatabaseConfig, logger.New, provideDB, provideGRPCServer,
)

// DomainSet 汇聚业务域 provider。新增 order 域时在这里加四行即可：
//   order.NewRepository, order.NewService, order.NewHandler, order.NewServer,
var DomainSet = wire.NewSet(
	todo.NewRepository, todo.NewService, todo.NewHandler, todo.NewServer,
	user.NewRepository, user.NewService, user.NewHandler, user.NewServer,
)

var AppSet = wire.NewSet(NewApp)   // S4 会追加 Registrar 切片 provider
```

```go
// cmd/server/wire.go —— 12 项扁平列表 → 语义三行
func InitApp(cfg *conf.Bootstrap) (*App, func(), error) {
	wire.Build(PlatformSet, DomainSet, AppSet)
	return nil, nil, nil
}
```

### S3b：抽 `internal/platform/httpx` + 合并 router.go（0.6 人天）

**新增**：`internal/platform/httpx/httpx.go`(~110 行)；**删**：`internal/{todo,user}/router.go`；**改**：两个 handler、`main.go`、`cmd/server/providers.go`

`httpx` 提供：`ReadBody` / `Validate` / `Bind` / `WriteProto` / `WriteError` / `WriteMapped` / `RequestLogger` / `NewValidator` / `type Registrar interface{ RegisterRoutes(gin.IRouter) }`。

- `NewValidator` 成为 wire provider → **3 个 protovalidate 实例收敛为 1 个**；连带 `NewHandler` 不再返回 error，wire 图少两个错误分支：
`func NewHandler(svc *Service, v httpx.Validator, log *slog.Logger) *Handler`
- `router.go` 的内容转为 `*Handler` 的方法，并加断言：

```go
var _ httpx.Registrar = (*Handler)(nil)
func (h *Handler) RegisterRoutes(r gin.IRouter) {
	g := r.Group("/api/v1/todos")
	{ g.POST("", h.Create); g.GET("", h.List); g.GET("/:id", h.Get); g.PATCH("/:id", h.Update); g.DELETE("/:id", h.Delete) }
}
```

- handler 方法瘦身为：`if !httpx.Bind(c, h.validate, &req) { return }` → `if err != nil { httpx.WriteMapped(c, h.log, err); return }` → `httpx.WriteProto(...)`。

**⚠️ 最大陷阱**：`Update` **不能**直接用 `httpx.Bind`——它必须先 `ReadBody` → 补 `req.Id = c.Param("id")` → 再 `Validate`（原 `todo/handler.go:108` 的注释已强调，顺序颠倒会让 id 的 uuid 规则对空值报错）。在 `Bind` 的 doc comment 里注明"仅用于无需补路径参数的场景"。

**关于 server.go 能否再薄**：诚实结论——**不能了**。它是纯转发，每方法已是「调用 / if err / 组装响应 / return」的下界（约 6 行）。评估过泛型 adapter（要在已知 err 后才组装响应，得不偿失）、`*Server` 嵌入 `*Service`（签名不同，必须转换且会让 proto 渗进 Service）、protoc 插件生成转发（投入产出比极低）——**全部否决，接受"必要之薄"**。

**验收**：改造前后跑同一份 API 黄金列表（todo 5 条 + user 关键路径 × Gin/gRPC）逐条 diff 状态码与响应体。

### S3c：`aipgorm` 增强 —— 抽取 List 骨架（0.4 人天）
